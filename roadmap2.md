# yaniktoim — Roadmap 2 (управление контентом) — план на будущее

Продолжение после закрытого `roadmap.md` (база, рендер, Worker-логин — сделаны).
Это **план**, не реализация. Реализуем после редизайна.

> Архитектурная рамка (неизменна): сайт — статика на gh-pages (`main /docs`),
> единый рендер `docs/editor/render.js` (Node-сборка + браузер), правка inline
> на самих страницах, коммиты через Cloudflare Worker (токен на Worker,
> author = ник). Источник истины — файлы в репо; html — производный.

---

## 0. Цель

Полноценное управление авторским сборником прямо на сайте (без отдельного
сервера-CMS): редактировать не только тексты статей, но и **структуру** —
главную и страницы разделов. Всё — через тот же inline-подход и Worker-коммиты.

## 1. Что уже есть (база)

- Статьи: `zml/<art>.zml` → `render.js` → `docs/<section>/<art>.html`; inline ✎
  на странице; атрибуция `editor`/`edited`; Save = один коммит через Worker.
- Логин по нику (Worker, KV), роли pending/editor/admin.
- Главная и страницы разделов генерит `src/5_index.py` из `manifest.json` — пока
  **не редактируемы** из браузера.
- Названия разделов: первоисточник — `src/1_fetch.py::SECTIONS` (слаг→книга
  proza.ru→имя). Сейчас продублированы в `5_index.py`/`render.js` (хрупко —
  именно там прошлая модель «тихо» переписала два; восстановлено, см. §3).

## 2. Требования оператора (целевые возможности)

1. **Редактируемые главная и страницы разделов** — отдельным образом (не ZML-
   текст, а структурный редактор списков).
2. **Разделы**: переименовать, менять порядок, добавлять новые, удалять.
3. **Статьи**: переименовать, менять порядок, добавлять, удалять, перемещать
   между разделами.
4. **Архив (soft-delete)**: удалённые статьи (и разделы) не исчезают, уходят в
   Архив, восстановимы — «рукописи не горят».
5. **Общий CMS-вид** (тот, что был отвергнут как отдельный сервер — теперь
   встроенный): страница-редактор списка раздела, где у каждого элемента —
   кнопка **Edit** (открывает правку статьи прямо тут, без отдельной страницы).

## 3. Модель данных — ЕДИНЫЙ источник структуры

Завести **один** источник структуры сайта (например `config/structure.json`),
из которого читают и сборка, и редактор. Он заменяет три захардкоженных копии
имён разделов (это и закрывает «канал утечки» из инцидента 2026-05-29).

```jsonc
{
  "sections": [
    { "slug": "best", "name": "Избранное", "order": 1, "archived": false,
      "intro": "" }              // intro — опц. вводный текст раздела
    // …
  ],
  "articles": [
    { "art": "VBL", "section": "shoshana", "title": "…", "order": 13,
      "status": "published" }    // status: published | archived
    // прочие метаданные (date/summary/image) остаются во frontmatter zml
  ]
}
```

- `manifest.json` (нынешний) можно эволюционировать в это или держать
  `structure.json` поверх него. Решить на старте фазы A.
- Имена/порядок разделов и статусы/порядок статей живут ТОЛЬКО здесь.
  `1_fetch.py::SECTIONS` остаётся для скрейпа, но имена для сайта берутся из
  `structure.json` (или генерятся в него из SECTIONS разово).

## 4. Консолидация рендера (как с 4_render→render.js)

Перенести генерацию главной и страниц разделов из `src/5_index.py` в
`render.js` (`renderIndex(structure)`, `renderSectionIndex(section, structure)`),
чтобы редактор пересобирал их **в браузере при Save** — так же, как статьи.
`build.mjs` строит index+разделы из `structure.json`. `5_index.py` → retired
(в `_backups/`), единый движок везде. (Снимает и дрейф имён разделов.)

## 5. Структурный редактор (встроенный «CMS»)

Админ-режим на главной и страницах разделов:
- На странице раздела ✎ → режим списка: drag-reorder статей, переименование,
  add/delete(→архив), перемещение в другой раздел; у каждой строки — **Edit**
  (открывает ZML-редактор статьи inline/в той же вкладке).
- На главной ✎ → редактор разделов: reorder, rename, add, delete(→архив).
- Дерево «всё сразу» (опц.): сводный admin-вид структуры (разделы+статьи) —
  это и есть возрождённый общий CMS, но как страница сайта, не сервер.
- Изменения структуры → пересборка `index.html` + затронутых `<section>/
  index.html` (+ статьи, если сменилось имя раздела в хлебных крошках) и
  один коммит через Worker.

## 6. Архив и восстановление

- Удаление = `status: "archived"` (НЕ физическое удаление). `zml` остаётся в
  репо (вариант: каталог `zml/` неизменен, скрытие — по статусу; либо перенос
  в `zml/_archive/` — решить). Из публичных списков скрыто.
- Страница **Архив** (admin): список архивных статей/разделов + «Восстановить»
  (флип статуса). 
- Глубинный бэкап и так есть — **git-история** хранит всё (даже при физическом
  удалении файла история остаётся). Архив — это UX-слой поверх.

## 7. Новые статьи (не из proza.ru)

- Создание = пустой `zml` из шаблона (frontmatter + тело) → сразу правка.
- **Минт art-id**: текущие id кодируют дату (SPEC §2.3), генерились
  `build_art_ids.py` из manifest+raw. Для новых нужен генератор нового id
  (на клиенте или в Worker), без коллизий. Спланировать в фазе E.
- Состояние **draft** (создана, ещё не опубликована) vs published — решить,
  нужен ли отдельный статус.

## 8. Модель сохранения / коммиты

- Все изменения (контент + структура) — через Worker **одним коммитом**.
  Обобщить `/api/save` до приёма списка файлов `files[]` (или `/api/save-batch`):
  `structure.json` + перегенерённые html + новые/изменённые `zml`.
- **Оптимистичная конкуренция**: Worker уже работает от head-sha ветки; при
  расхождении (другой редактор успел) — отказ/повтор, чтобы не затирать чужое.
- Атрибуция структурных правок: кто менял (тот же author=ник; опц. лог в
  коммит-месседже «structure: reorder sections by <ник>»).

## 9. Роли

- `editor` — контент статей (правка текста, создание).
- `admin` — структура (разделы add/delete/rename/reorder), архив/восстановление,
  перемещение статей между разделами. (Точную границу уточнить.)

## 10. Стабильность URL

- Переименование **отображаемого имени** раздела — слаг не меняется, URL
  стабилен (безопасно).
- **Перемещение статьи** между разделами меняет URL `docs/<section>/<art>.html`
  → решить: оставлять redirect-заглушку на старом пути или принять смену URL.
- Удаление слага раздела (а не имени) — ломает URL; вероятно запретить менять
  слаг через UI (слаги — твои, фиксированы), менять только `name`.

## 11. Открытые вопросы (нужно решение оператора)

1. **«Избранное» — это раздел или сквозная подборка?** Сейчас у статьи ровно
   один `section`. Если «Избранное» = featured-витрина поверх настоящих
   сборников, нужна пометка `featured` (многие-ко-многим), а не отдельный
   раздел. Как у тебя по смыслу proza.ru?
2. **manifest.json vs новый structure.json** — эволюционировать существующий
   или завести отдельный поверх? (влияет на пайплайн).
3. **Архив**: скрывать по статусу (файлы на месте) или физически переносить в
   `zml/_archive/`? (статус проще и безопаснее).
4. **draft-статус** для новых статей нужен?
5. **Вводный текст/обложка раздела** (`intro`, картинка) — нужны на страницах
   разделов?
6. **Закреплённые/выделенные** статьи внутри раздела (pin) — нужны?
7. **Sitemap/SEO**: пересобирать `sitemap.xml` при изменении структуры?
8. **Конкурентные правки** двух админов — достаточно «отказ+повтор», или нужен
   мягкий мерж?

## 12. Предлагаемые фазы (порядок реализации)

- **A. Единый источник структуры** — `structure.json` (из `1_fetch.py::SECTIONS`
  + manifest), порт index/section-рендера в `render.js`, `build.mjs` строит из
  него; `5_index.py` retired. Побочно закрывает дрейф имён разделов. *(Низкий
  риск, высокая отдача — делать первым.)*
- **B. Admin-вид структуры (read-only дерево)** — страница со структурой
  (разделы+статьи), gated по роли admin. Каркас редактора.
- **C. Reorder + rename** разделов и статей (порядок, отображаемые имена) +
  Save через Worker (один коммит, оптимистичная конкуренция).
- **D. Архив/восстановление** (soft-delete) + страница Архив.
- **E. Создание статей** (пустой zml, минт art-id, draft) + удаление в архив.
- **F. Перемещение статей между разделами** + политика URL/redirect.
- **G. Add/delete разделов** (с учётом фиксированных слагов / запрета смены slug).
