## 0. Цель

Полноценное управление авторским сборником прямо на сайте (без отдельного
сервера-CMS): редактировать не только тексты статей, но и **структуру** —
главную и страницы разделов. Всё — через тот же inline-подход и Worker-коммиты.

## 1. Что уже есть (база)

- Статьи: `zml/<art>.zml` → `render.js` → `docs/<section>/<art>.html`; inline ✎
  на странице; атрибуция `editor`/`edited`; Save = один коммит через Worker.
- Логин по нику (Worker, KV), роли pending/editor/admin.
- Главная и страницы разделов генерит `src/5_index.py` из `manifest.json` — пока
  **не редактируемы** из браузера.
- Названия разделов: первоисточник — `src/1_fetch.py::SECTIONS` (слаг→книга
  proza.ru→имя). Сейчас продублированы в `5_index.py`/`render.js` (хрупко —
  именно там прошлая модель «тихо» переписала два; восстановлено, см. §3).

## 2. Требования оператора (целевые возможности)

1. **Редактируемые главная и страницы разделов** — отдельным образом (не ZML-
   текст, а структурный редактор списков).
2. **Разделы**: переименовать, менять порядок, добавлять новые, удалять.
3. **Статьи**: переименовать, менять порядок, добавлять, удалять, перемещать
   между разделами.
4. **Архив (soft-delete)**: удалённые статьи (и разделы) не исчезают, уходят в
   Архив, восстановимы — «рукописи не горят».
5. **Общий CMS-вид** (тот, что был отвергнут как отдельный сервер — теперь
   встроенный): страница-редактор списка раздела, где у каждого элемента —
   кнопка **Edit** (открывает правку статьи прямо тут, без отдельной страницы).
6. **Иллюстрация статьи в ZML-редакторе** (оператор 2026-06-18): загрузить /
   заменить / удалить картинку вверху статьи (frontmatter `image:`, хранилище
   `docs/img/`). Детали/план — `imyavel/roadmap_cms.md`, блок «Запланировано» п.2.
7. **«Песнь Ступеней» редактируема как обычная ZML-страница** (оператор
   2026-06-18): ✎ на `songs/index.view.html` + браузерный рендер-паритет с
   `build_songs.mjs`. Детали/план — там же, п.3.

## 3. Модель данных — ЕДИНЫЙ источник структуры

Завести **один** источник структуры сайта (например `config/structure.json`),
из которого читают и сборка, и редактор. Он заменяет три захардкоженных копии
имён разделов (это и закрывает «канал утечки» из инцидента 2026-05-29).

```jsonc
{
  "sections": [
    { "slug": "best", "name": "Избранное", "order": 1, "archived": false,
      "intro": "" }              // intro — опц. вводный текст раздела
    // …
  ],
  "articles": [
    { "art": "VBL", "section": "shoshana", "title": "…", "order": 13,
      "status": "published" }    // status: published | archived
    // прочие метаданные (date/summary/image) остаются во frontmatter zml
  ]
}
```

- **Принадлежность статьи к разделу — во frontmatter `zml`** (`section:`, и
  `section_order:`/`order:`). Это свойство самой статьи → «переместить в раздел»
  = правка frontmatter, которую редактор и так коммитит. Источник истины для
  раздела статьи = её frontmatter (НЕ manifest).
- **`structure.json` собирается (derived)** сборкой: список/имена/порядок
  разделов — из него самого (seed из `1_fetch.py::SECTIONS`); принадлежность
  статей — скан `section:` во всех `zml`. `manifest.json` тоже становится
  производным от скана frontmatter (или сливается в `structure.json`). Так раздел
  не дублируется и не разъезжается (текущая `manifest.section` — временно, до
  фазы A; тогда же `render.js` начнёт читать `fm.section`, а не `rec.section`).
- Имена/порядок разделов живут в `structure.json`; `1_fetch.py::SECTIONS` —
  только seed для скрейпа.

> ⚠ Почему не сейчас кусочно: если записать `section:` во frontmatter, пока
> индексы строит `manifest.section`, ручная правка раздела в textarea разъедется
> с manifest. Делаем атомарно в фазе A (frontmatter→derive).

## 4. Консолидация рендера (как с 4_render→render.js)

Перенести генерацию главной и страниц разделов из `src/5_index.py` в
`render.js` (`renderIndex(structure)`, `renderSectionIndex(section, structure)`),
чтобы редактор пересобирал их **в браузере при Save** — так же, как статьи.
`build.mjs` строит index+разделы из `structure.json`. `5_index.py` → retired
(в `_backups/`), единый движок везде. (Снимает и дрейф имён разделов.)

## 5. Структурный редактор (встроенный «CMS»)

> **ИНВАРИАНТ ВЁРСТКИ (требование оператора 2026-06-18):** после появления
> правки/перемещения/добавления в списках разделов и статей **ширина строки и
> межстрочные промежутки в этих списках НЕ должны увеличиться** относительно
> текущего комфортного вида. Редактор структуры рендерит ТОТ ЖЕ markup списка
> (`ul.toc` / карточки раздела) с теми же `style.css`-правилами; служебные
> контролы (drag-ручки, кнопки Edit/↑↓/✕) добавляются БЕЗ роста line-height и
> ширины строки (например, абсолютным позиционированием/оверлеем, а не вставкой
> в поток, раздвигающей строки). Проверять зрением до/после на списках разделов.

Админ-режим на главной и страницах разделов:
- На странице раздела ✎ → режим списка: drag-reorder статей, переименование,
  add/delete(→архив), перемещение в другой раздел; у каждой строки — **Edit**
  (открывает ZML-редактор статьи inline/в той же вкладке).
- На главной ✎ → редактор разделов: reorder, rename, add, delete(→архив).
- Дерево «всё сразу» (опц.): сводный admin-вид структуры (разделы+статьи) —
  это и есть возрождённый общий CMS, но как страница сайта, не сервер.
- Изменения структуры → пересборка `index.html` + затронутых `<section>/
  index.html` (+ статьи, если сменилось имя раздела в хлебных крошках) и
  один коммит через Worker.

## 6. Архив и восстановление

- Удаление = `status: "archived"` (НЕ физическое удаление). `zml` остаётся в
  репо (вариант: каталог `zml/` неизменен, скрытие — по статусу; либо перенос
  в `zml/_archive/` — решить). Из публичных списков скрыто.
- Страница **Архив** (admin): список архивных статей/разделов + «Восстановить»
  (флип статуса). 
- Глубинный бэкап и так есть — **git-история** хранит всё (даже при физическом
  удалении файла история остаётся). Архив — это UX-слой поверх.

## 10. Стабильность URL — РЕШЕНО (плоская схема)

- **[СДЕЛАНО 2026-05-29]** Статьи переведены в плоский каталог
  **`docs/art/<art>.html`**, не зависящий от раздела. Раздел — только
  метаданные (`manifest.section`). → перемещение статьи между разделами
  **не меняет URL**, редиректы не нужны. Внутренние `[[art]]` и prev/next —
  same-dir; страницы разделов (`docs/<section>/index.html`) ссылаются на
  `../art/<art>.html`; крошки статьи на раздел — `../<section>/index.html`.
- Переименование отображаемого имени раздела — слаг не меняется (безопасно).
- Смена слага раздела через UI — запретить (слаги фиксированы оператором),
  менять только `name`.
