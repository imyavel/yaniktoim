# Диагностика повторяющейся ошибки 400 «thinking blocks cannot be modified»

Дата: 2026-05-29 · Инструмент: Claude Code CLI 2.1.119 · Модель: `claude-opus-4-8` · Режим: `claude -p`, `--permission-mode bypassPermissions`, extended thinking (adaptive)

---

## 1. ВЕРДИКТ — наиболее вероятная причина

**Это клиентский (Claude Code) баг сериализации/пересборки истории при extended thinking + tool use, а НЕ проблема API и НЕ следствие кириллицы. Уверенность: высокая (~90%).**

Механизм (подтверждён транскриптами + первоисточником-issue #63147):

1. Claude Code сохраняет в транскрипт (`projects/<slug>/<id>.jsonl`) каждый `thinking`-блок с **обнулённым телом** (`"thinking": ""`), но **сохраняет поле `signature`** (опаковый шифрованный base64-токен, 368–1364 симв.).
2. При построении СЛЕДУЮЩЕГО запроса в рамках той же сессии (очередной/догоняющий промпт — у нас финальный шаг «напечатай резюме») клиент пересобирает массив `messages` из этого транскрипта и отправляет блоки в виде `{"type":"thinking","thinking":"","signature":"<оригинал>"}`.
3. Сервер по `signature` восстанавливает оригинальный (непустой) текст thinking; пустое тело ему противоречит → блок считается «изменённым» → **400 invalid_request_error: «`thinking` … blocks … cannot be modified»**.

Почему всегда `messages.1`: это ПЕРВОЕ ассистентское сообщение — туда попадает самая ранняя цепочка подписанных thinking-блоков. Разные `content.56` / `content.16` — это просто позиция конкретного обнулённого-но-подписанного thinking-блока внутри длинного первого ассистентского сообщения; индекс меняется с длиной/структурой прогона.

### Доказательная база из транскриптов
- Транскрипты с ошибкой: `bbf06c76-…jsonl` (req `req_011CbXBBGuGH7PRTi4zAqP6X` — совпадает с `_logs_prose_synthesis.log`, content.56) и `94b6cc1d-…jsonl` (req `req_011CbWnmVMtRNi62EJUuNumr`, content.16).
- **Все `thinking`-блоки имеют `signature`, но тело пустое (`len=0`)** — проверено на сырых строках (L7/31/62/86 в bbf06c76). Поля `redacted_thinking` НЕТ нигде.
- В `94b6cc1d` ошибка указывает `content.16`, **а во всём транскрипте логировано лишь 14 ассистентских блоков** → отправленный `messages[1]` содержал БОЛЬШЕ блоков, чем чистая поблочная запись. Это прямое свидетельство, что исходящий запрос — продукт ПЕРЕСБОРКИ, а не зеркало одного прохода.
- Ошибочная запись (L89/L27) имеет `model:"<synthetic>"` и `isApiErrorMessage:true, apiErrorStatus:400` — это синтетическая запись CLI об ответе API (т.е. 400 пришёл от сервера на запрос, собранный клиентом).
- В сессиях присутствуют множественные маркеры `queue-operation` и `last-prompt` (bbf06c76: L64, L88, L90) — то есть в одной сессии обрабатывалось НЕСКОЛЬКО промптов; именно догоняющий промпт пересобирает историю и падает.
- **Признаков авто-компакции НЕТ**: ни `isCompactSummary`, ни `compactMetadata`, ни summary-узлов. → У нас сработал путь «пересборка из транскрипта при очередном промпте», а не компакция (компакция — родственный, но другой триггер того же класса бага, см. issue #13012).

### Подтверждение первоисточниками
- **Issue #63147** (anthropics/claude-code, open, есть repro) дословно описывает тот же механизм: «persists … with the `thinking` text emptied to `""` but the `signature` field retained» → при resume «permanently broken state», 400. Версия в репорте 2.1.153 — баг версионно-независимый (это дефект схемы хранения/пересборки), наша 2.1.119 в том же классе.
- **Docs (Building with extended thinking)**: «During tool use, you must pass `thinking` blocks back … the **complete unmodified block**»; «the entire sequence of consecutive `thinking` blocks must match the outputs … you can't rearrange or modify»; «The server **decrypts the `signature` to reconstruct the original thinking**». То есть валидация идёт по подписи, тело должно соответствовать оригиналу.

## 2. Оценка выдвинутой гипотезы (не-ASCII / кириллица + глифы)

**ОПРОВЕРГАЕТСЯ как прямая причина. Частично допустима лишь как косвенный усилитель.**

Аргументы против юникод-нормализации подписи:
- **`signature` — непрозрачный шифрованный токен** (base64, начинается с `Eo0C…`, `Es0C…` — protobuf-обёртка), он НЕ содержит кириллицы и не является хешем видимого текста, который клиент мог бы «перенормализовать». Docs: сервер сам **расшифровывает** signature, чтобы восстановить thinking. Кириллица в теле не участвует в вычислении подписи на стороне клиента.
- Реальная «модификация» в наших данных — это **обнуление тела до `""`**, а не побайтовое изменение кириллицы. Тело стало пустым — вот что не сходится с подписью.
- Claude Code сериализует запрос через JSON (UTF-8) без шага NFC/NFD-нормализации; кириллица и глифы `<\^/>`, `;;;;`, `;::)))` кодируются стабильно.
- **Решающее контр-доказательство:** те же задачи с той же кириллицей **проходили при перезапуске** (логи `v2_editorial/run.log`, `_logs_prose_synthesis` итог записан). Будь причиной детерминированная побайтовая порча из-за кириллицы — повторы тоже падали бы. Они не падали → недетерминизм указывает на пересборку/тайминг, а не на контент.

Где не-ASCII может играть КОСВЕННУЮ роль (гипотеза, не доказано): тяжёлый литературный текст → больше «размышлений» и больше шагов Read/Write → длиннее цепочка подписанных thinking-блоков в `messages[1]` и больше догоняющих ходов → выше вероятность нарваться на баг пересборки. Это влияние через ОБЪЁМ/число блоков, а не через байты подписи.

## 3. Ранжированные альтернативные причины

1. **(основная) Клиентская пересборка истории из транскрипта с обнулённым телом thinking при сохранённой подписи.** Доказано транскриптами (пустое тело + signature; content.16 при 14 логированных блоках) и issue #63147.
2. **Накопление длинной interleaved-цепочки thinking+tool_use в одном первом ассистентском сообщении (`messages.1`).** Доказуемо: id `…QXyA1rS3` охватывает L7–62 с tool_result между ними; индексы 56/16 живут в первом ассистентском сообщении. Это «среда», в которой проявляется баг №1.
3. **Очередь/догоняющие промпты в одной сессии (`queue-operation`, несколько `last-prompt`).** Доказуемо из маркеров. Именно второй+ запрос пересобирается и падает — объясняет недетерминизм «до/после Write».
4. **Авто-компакция, задевающая подписанный блок** (родственный путь, issue #13012). **В наших транскриптах НЕ обнаружена** (нет compact-маркеров) — для данных прогонов отвергается, но остаётся общим триггером того же класса.
5. **Гонки параллельных фоновых сессий в одном проект-каталоге.** Возможный усугубляющий фактор (много jsonl в одном `C--design-lab`), но **прямых доказательств перекрёстной записи нет**; каждая ошибка локализована в своём файле с собственным request_id. Низкая вероятность как первопричина.
6. **Баг конкретно версии 2.1.119.** Маловероятно как уникальная причина: тот же дефект отражён в issue для 2.1.153 и ранее → это устойчивый дефект схемы, а не регрессия одной сборки.

## 4. Что доказуемо, а что осталось гипотезой

**Доказуемо (из транскриптов/логов):**
- thinking-блоки хранятся с пустым телом и сохранённой подписью; `redacted_thinking` отсутствует.
- Отправленный `messages[1]` содержал больше блоков, чем чисто логировано (content.16 vs 14) → запрос пересобран.
- 400 пришёл от API (синтетическая запись CLI), request_id совпадает с логом synthesis.
- Авто-компакция в этих сессиях не задействована.
- Те же кириллические задачи успешно завершались при перезапуске.

**Осталось гипотезой (не доказано напрямую данными):**
- Точный код-путь внутри 2.1.119 (resume vs queue vs внутренняя дозагрузка транскрипта) — вывод опирается на маркеры + issue, исходник CLI не читался.
- Косвенное влияние объёма не-ASCII на вероятность бага — правдоподобно, но не измерено.
- Роль гонок параллельных сессий — не подтверждена.

## 5. Митигации (по убыванию эффективности)

1. **Убрать многошаговость из одной сессии: один `claude -p` = одна атомарная задача.** Не добавлять догоняющий промпт «напечатай резюме» в ту же сессию — пусть агент пишет файл И печатает итог в первом же проходе. Это устраняет шаг пересборки истории, на котором всё ломается. (Самое надёжное и сразу применимое.)
2. **Не использовать `--resume`/`--continue` для сессий с extended thinking + tool use.** Для нового шага — новая сессия с явно переданным контекстом (путь к уже записанному файлу), а не продолжение старой.
3. **Отключить extended thinking для headless-пайплайна, где оно не нужно** (`--thinking`/настройка уровня → off, либо модель/режим без interleaved thinking). Нет подписанных thinking-блоков → нечему «модифицироваться». Хорошо подходит для механических Write/format-задач.
4. **Обновить Claude Code** и отслеживать issue #63147 / #13012 (на 2026-05-29 — open, фикса нет). Проверять, не появилась ли защита «не отправлять thinking-блок с непреобразованным телом».
5. **Идемпотентность прогонов:** писать файл ДО финального резюме и считать прогон успешным по факту файла; парсить stdout-итог как необязательный. Снижает урон (терять только текстовый итог, не результат). Подтверждено наблюдением: в synthesis файл уцелел, потерян лишь stdout.
6. **Изоляция рабочих каталогов на параллельные прогоны** (свой проект-slug/каталог на поток), чтобы исключить любые гонки записи транскрипта — дёшево, страхует альтернативу №5.
