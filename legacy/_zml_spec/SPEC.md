# ZML — yaniktoim Markup Language (draft v0.1)

Текстовый формат хранения статей `yaniktoim-cms`. Заменяет JSON-блочную структуру и встроенный частичный HTML внутри полей `html`. Один источник правды для всего пайплайна:

```
raw HTML (proza.ru)
       │
       │ 3_transform.py (headless claude -p)
       ▼
   <NNN>.zml   ◄── source of truth, редактируется в CMS
       │
       │ 4_render.py (ZML → HTML)
       ▼
   site/<section>/NNN.html
```

---

## 1. Структура документа

```
---
<frontmatter — YAML, обязательный>
---

<блоки до первой секции (intro)>

## <Заголовок секции> {anchor}
<блоки в этой секции>

## <Следующая секция>
...

[^1]: <тело нумерованной сноски 1>
[^2]: <тело нумерованной сноски 2>

[^]: <тело анонимной сноски (рендер ставит префикс «См. также:»)>
[^|Дополнение]: <тело анонимной с кастомным префиксом>
```

Порядок:
1. `---`-обёрнутый frontmatter (всегда первый).
2. Один или несколько блоков (intro — до первой `##`-секции).
3. Ноль или несколько секций, каждая начинается с `## ...`.
4. Сноски (если есть) — всегда в самом конце документа, ОДНИМ блоком. Нумерованные `[^N]:` идут первыми, анонимные `[^]:` / `[^|...]:` — после, разделённые от нумерованных пустой строкой (необязательно, но желательно для читаемости source).

Никакого служебного «`# Заголовок`» в теле — заголовок статьи всегда в frontmatter (`title:`).

## 2. Frontmatter

```yaml
---
title: Летопись Живого Огня
summary: Стихи Бар Малея о связи половой любви и духовной веры, очищении Землёй и Огнём.
art: "182"
date: 2 Августа 2021 г.
---
```

| Поле | Тип | Обязательно | Назначение |
|------|-----|-------------|------------|
| `title` | string | да | `<h1>` статьи, breadcrumb, `<title>` страницы |
| `summary` | string ≤ 160 | нет | `<meta name="description">` |
| `art` | string | да | **Арт-id статьи** в формате `XYZ` или `XYZ<n>` (см. §2.3). Кодирует date_chosen статьи. Универсальный идентификатор: используется как имя `.zml`/`.html` файла, в `[[<art>]]`-ссылках и в colophon. Авторские арт-номера из тела proza-исходника (`AP182`, `XX01`...) уже выкидываются на этапе transform — у нас своя унифицированная система. |
| `date` | string | нет | Дата написания в авторском формате (`2 Августа 2021 г.`, `Декабрь 2023`, `08 марта 2024` и т.п.). У прозы указывается **часто**, в разных форматах. Если задана — **переопределяет** `date_display` из `manifest.json` (которая вычислена из URL `proza.ru/YYYY/MM/DD/NNN`). Если не задана — fallback к URL-дате. |
| `image` | string | нет | Имя файла cover-картинки в папке `pics/`. Например `image: 1695.jpg` → рендер берёт `/pics/1695.jpg`. У proza.ru-исходников inline-картинок не было, оператор задаёт вручную при post-edit в CMS. |

(Поля `section`, `origin_url` берутся из `manifest.json` и в ZML не дублируются — это структурные данные, не контент.)

### 2.1. Где отображается art / date

- **Сверху, в byline** — `date` (если задан), иначе `date_display` из manifest. Формат:
  `Элиягу Бар Малей · #<art> · <date> · Оригинал: …`
- **Внизу, в colophon** — отдельный параграф `<p class="colophon">` перед блоком сносок:
  - Если оба заданы: `Арт. #182, записано 2 Августа 2021 г.`
  - Если только дата: `Записано 2 Августа 2021 г.`
  - Если только арт: `Арт. #182`
  - `art` обязателен в frontmatter — но рендер всё равно проверяет наличие, чтобы не падать на пустом значении.

Символ `#` префиксируется при отображении; в самом `frontmatter.art` хранится без него (`art: "182"`, `art: "1B5"`, `art: "247A"`).

### 2.2. Извлечение из исходника на этапе transform

`3_transform.py` (LLM-pass) при разборе proza.ru-сырья:
- `art` — заполняется автоматически из реестра в `manifest.json` (поле `art`, генерируется разово скриптом `src/build_art_ids.py` на этапе сборки манифеста). Авторские `Арт. #AP182`-сигнатуры в теле находит и **удаляет** или заменяет на наш `art` (см. ниже §2.3 и roadmap → TODO).
- `date` — распознаёт свободно-форматные даты в теле (`«N месяца YYYY г.»`, `«Записано N месяца YYYY»`, `«Написано в <месяц> <год>»`, `«<месяц> <год>»` и т.п.). Если найдено — извлекает в frontmatter и удаляет из тела. Если не найдено — поле остаётся пустым, рендер использует `manifest.date_display` (URL-дату) как fallback.

### 2.3. Формат арт-id: `XYZ[n]`

Все id в системе строятся по единому правилу из **date_chosen** статьи (author-date если есть в тексте, иначе url-date), плюс опциональный суффикс для нескольких статей в одну дату.

```
X — год
Y — месяц (1-9, A=10, B=11, C=12)
Z — день  (1-9, A=10, ..., V=31)
n — опционально: A..Z, потом a..z для multi-per-day (без точки-разделителя)
```

**Шкала года `X`** (один символ):
- `0` = 2020, `1` = 2021, ..., `9` = 2029 — текущий рабочий диапазон.
- `Z` = 2019, `Y` = 2018, `X` = 2017, ... , `A` = 1994 — обратная шкала для редких ранних черновиков.

(Год ≥ 2030 пока не покрывается. У автора более ранних обновлений не ожидается до конца проекта.)

**Multi-per-day suffix `n`**:
- 1 статья за день — без суффикса. Пример: `182` (2 августа 2021).
- 2-я статья того же дня — `182A`.
- 3-я — `182B`. И так далее до `Z`.
- После `Z` — `a`, `b`, ..., `z` (всего 25 + 26 = 51 дополнительных + первичная = **52 на день максимум**).
- 52-я — ошибка парсера (warning при build_art_ids).

**Порядок присваивания** при нескольких статьях с одинаковой date_chosen — по `url_nnn` ascending. То есть статья с меньшим NNN на proza.ru получает чистый `XYZ`, следующая — `XYZA`, и т.д.

**Преимущества**:
- id сам кодирует дату — легко вставить «найденную старую» статью без сдвига последующих.
- Сортировка корпуса по дате тривиальная.
- Короткий — 3-4 символа (vs 3-значный NNN со сдвигами).

**Авторские арт-номера в теле** (типа `#AP182`, `#AA11H` — серия + год + месяц + день):
- Если арт-номер совпадает с реальной датой статьи (по date-decode) — `3_transform.py` **заменяет** его на наш канонический id (одна и та же статья — один и тот же id, серия больше не используется).
- Если арт-номер в colophon-формате (`Арт. #AP182, написано 2 Августа 2021 г.`) — удаляется (как и сейчас).
- Если арт-номер ссылается на **другую** статью корпуса (по date-decode → lookup в `manifest.json` по `art`) — заменяется на `[[<art>]]` (внутренняя ссылка).
- Если арт-номер расшифровывается в дату, для которой в корпусе нет статьи (broken) — оставляется как `<span class="broken">[[<art>]]</span>` с warning в build log.

## 3. Секции (h2)

```
## АКТ ПЕРВЫЙ И АКТ ВТОРОЙ. ПОЛОВАЯ ЛЮБОВЬ И ДУХОВНАЯ ВЕРА {akt-1-2}
```

- Строка вида `## <текст> {<slug>}`.
- `{<slug>}` опциональный: если не задан, генерируется автоматически (`slugify(text)`).
- Секция длится до следующего `## ...` либо до начала блока сносок (`[^N]:`), либо до конца документа.
- Текст в CAPS — нормальная практика; рендер автоматически downcase + capitalise first letter of each sentence + восстанавливает имена собственные (Орёл, Творец, Адам, Господь, Бог, Ева, Шхина).

Заголовок H1 в теле не пишется. Подразделов глубже (H3) в текущей коллекции нет — поэтому в ZML не зарезервированы.

## 4. Блоки

Блоки отделены друг от друга **пустой строкой**.

### 4.1. Параграф (default)

Просто текст без обрамляющих тегов. Может занимать несколько строк, но без пустых строк внутри (пустая строка = конец параграфа).

```
Сила в стихах о Сказке, гораздо более реальной, чем то, что мы привыкли называть "жизнь".

О связи духовной Любви и материальной любви.
```

Рендерер определяет специальные подвиды по позиции и контексту:
- `class="attribution"` — короткие лидирующие 1–3 строки в самом начале статьи (до первой пустой строки или эпиграфа). Авто.
- `class="colophon"` — **не извлекается из тела ZML**. Полностью генерируется из `frontmatter.art` / `frontmatter.date` (см. §2.1). Авторские арт-сигнатуры (`Арт. #AP182`) и текстовые даты (`Записано 2 Августа 2021 г.`), если попались на этапе transform, уже удалены из тела парсером и переехали во frontmatter.

Принудительно эти классы в ZML не указываются.

### 4.2. Нумерованная группа параграфов: `[num]...[/num]`

Когда несколько параграфов образуют именованную логическую последовательность (тезисы, шаги, пронумерованные правила), оборачиваются в `[num]...[/num]`. Параграфы внутри отделяются пустыми строками, как обычно; **рендер сам ставит нумерацию** «1.», «2.», «3.» перед каждым — оператор не пишет цифры в source.

```
Вводный параграф (без обёртки).

[num]
Первый тезис в нумерованной последовательности.

Второй тезис — рендер поставит «2.» перед ним автоматически.

Третий тезис может занимать несколько строк подряд внутри одного абзаца,
но без пустых строк (иначе разделится на два пункта).
[/num]

Заключительный параграф (тоже без обёртки).
```

Рендер:
```html
<ol class="num">
  <li>Первый тезис в нумерованной последовательности.</li>
  <li>Второй тезис — рендер поставит «2.» перед ним автоматически.</li>
  <li>Третий тезис может занимать несколько строк подряд внутри одного абзаца, но без пустых строк (иначе разделится на два пункта).</li>
</ol>
```

- Внутри пунктов работает обычная inline-разметка: `[^N]`, `[[nnn]]`, `{chapter|N}`, `[url|анкор]`, CAPS-pass, `^СЛОВО`.
- Тег для **одиночного** параграфа не существует — параграф остаётся default. `[num]` только тогда, когда нужна семантика «нумерованная последовательность».
- Внутри `[num]` допустимы только параграфы (текст между пустыми строками). Другие теги (`[poem]`, `[epi]` и т.п.) — это уже **разные блоки**, они должны быть вне `[num]`.

### 4.3. Стих

```
[poem]
Свет наполнит это Кли[^1]
Трепетной любовью
Ты держи Его внутри
Как свое, родное.
[/poem]
```

Несколько строф — разделены пустой строкой внутри `[poem]...[/poem]`:

```
[poem]
Чтобы в твоем ей быть распоряженьи
Силой, источник Которой древнее,

В этом Огне суть Вселенной и Бога
Нашего Господа, Бога Живого,
[/poem]
```

Опциональный title:
```
[poem title="Сказка"]
...
[/poem]
```

Поведение:
- Каждая строка — отдельная строка стиха.
- Ведущие пробелы строки сохраняются (важно для авторской «лесенки»).
- Каждая строка автоматически капитализируется по первой букве (Russian poetry convention).
- CAPS-строки (целые подряд) → small-caps, соседние CAPS-строки склеиваются в один `<span class="sb">` с сохранением пустых строк-строф.

### 4.4. Эпиграф

```
[epi]
Текст эпиграфа абзац 1.

Текст эпиграфа абзац 2.
[/epi]
```

С указанием источника (только если в исходнике источник стоит **в той же строке** что и текст эпиграфа — иначе оставлять как часть тела):

```
[epi cite="К. Кастанеда"]
Воин выбирает свой путь сердца.
[/epi]
```

Несколько эпиграфов подряд — каждый в своём блоке (рендер автоматически ставит метку «Эпиграф» в правом верхнем углу каждого):

```
[epi]
Первый эпиграф.
[/epi]

[epi]
Второй эпиграф.
[/epi]
```

### 4.5. Эпилог *(спящий, до первого появления в исходниках)*

```
[epil]
...
[/epil]
```

То же что эпиграф, но метка «Эпилог». CSS-класс `.epilogue` и рендер уже готовы; синтаксис закреплён, но в текущей коллекции из 350 статей не встречается — активируется при первом обнаружении на этапе ревизии pipeline.

### 4.6. Цитата (blockquote) *(спящая, до первого появления в исходниках)*

```
[quote cite="Бааль Сулам"]
Только наполнение Светом с Его последующим исчезновением делает Кли пригодным.
[/quote]
```

Метка «Цитата», прижата к левому краю (зеркало эпиграфа). Аналогично эпилогу — синтаксис зарезервирован, в текущей коллекции не встречается.

### 4.7. Подзаголовок (h2-эхо)

```
[sub]Летопись Живого Огня[^1][/sub]
```

Используется когда первое тело статьи дублирует заголовок H1 (часто с inline-сноской). Рендер ставит `<h2 class="subtitle">`.

### 4.8. Музыка: `[mus]...[/mus]`

Парный тег-контейнер. Внутри — список треков, каждый отдельной строкой в формате `[url|title|author]`. Опциональный атрибут `[mus="<заголовок>"]` задаёт label для всей группы.

Без кастомного заголовка (default «Музыка под настроение»):
```
[mus]
[https://youtu.be/5DBuIhr1Id4|Let Us Burn|Within Temptation]
[https://youtu.be/oAycSf8COQo|Sanitarium|Metallica]
[https://youtu.be/yLUOwe9f2X8|Это за окном Рассвет|Браво]
[|Песня без рабочей ссылки|Неизвестный исполнитель]
[/mus]
```

С кастомным заголовком:
```
[mus="Песнь Ступеней"]
[https://youtu.be/abc|Псалом 1|Псалмопевец]
[https://youtu.be/def|Псалом 2|Псалмопевец]
[/mus]
```

#### 4.8.1. Формат трек-строки внутри `[mus]`

```
[url|title|author]
```

Три параметра разделены `|`. **Достаточно одного любого** чтобы строка считалась валидной — пустые параметры допустимы:
- `[url|title|author]` — все три, классический случай.
- `[url|title|]` — без автора, в шапке только title.
- `[url||]` или `[url]` — только URL, анкор = сам URL.
- `[|title|author]` — без URL, `music-noplayer`.
- `[||author]` — без URL и title, в шапке только author.
- Пустая строка или `[|||]` — игнорируются парсером.

Поведение по URL:
- **YouTube** (`youtu.be/...` или `youtube.com/watch?v=...`) → `<details class="music">` с lazy iframe, caret, `↗`.
- **Другая платформа** → `<p class="music-flat">` (плоская строка с ссылкой; анкор — «author — title» либо сам URL).
- **Нет URL** → `<div class="music-noplayer">`, визуально как шапка большого блока без player.

#### 4.8.2. Группировка

Группа = всё внутри одного `[mus]...[/mus]`. Label единый для всей группы — через `[mus="<заголовок>"]` или дефолт «Музыка под настроение». В выходном HTML:

```html
<div class="music-group" data-label="Музыка под настроение">
  <details class="music">…1…</details>
  <details class="music">…2…</details>
  <div class="music-noplayer">…3…</div>
</div>
```

Поведение:
- Label рендерится **один раз** над группой через CSS `::before` + атрибут `data-label`.
- Внутри каждого трек-элемента — `<span class="label">` отсутствует (label вынесен на уровень группы).
- Треки склеены вертикально с минимальным зазором; каждый `<details>` раскрывается самостоятельно.
- Несколько `[mus]` блоков подряд (с разными label или с другим контентом между) — это разные группы, каждая со своей шапкой.

Trailing-music на конце статьи: если рендер автоматически ставит дополнительный `<h2 id="music">Музыка под настроение</h2>` перед группой (текущая логика `render_section` для статей с music в самом конце), `.music-group::before` подавляется через `.music-group.has-heading`.

#### 4.8.3. Warning при использовании трек-формата вне `[mus]`

Если парсер встречает `[a|b|c]` (три параметра с двумя разделителями `|`) **вне** `[mus]`-блока — это синтаксическая ошибка. В build-лог выводится:

```
WARN <NNN>.zml line <N>: Improper music link outside [mus]: [a|b|c]
```

В HTML вставляется `<span class="broken">[a|b|c]</span>` (видно в превью).

## 5. Inline-разметка

Внутри параграфа, строки стиха, эпиграфа, цитаты, тела сноски.

### 5.1. Маркер сноски

```
...Свет наполнит это Кли[^1] Трепетной любовью...
```

`[^N]` где `N` — id соответствующей сноски в блоке сносок. Рендер превращает в `<sup id="cite_ref-N"><a href="#cite_note-N">[N]</a></sup>` со всплывающим popup на hover.

### 5.2. Гиперссылка: `[url|анкор]`

```
См. также: [http://example.com/page|Подходящая работа].
```

- Анкор опционален. `[http://example.com]` (без `|`) — анкор равен самому URL.
- `[http://example.com|]` (пустой анкор после `|`) — то же что без `|`.
- Разделитель `|` — единственный. Экранирование `\|` если когда-нибудь встретится в анкоре (редчайший случай).
- Парсер вытаскивает `[url|анкор]` после footnote-маркеров `[^N]`, internal-ссылок `[[nnn]]` и Zohar-ссылок `{chapter|N}`, но **до** italic-pass и CAPS-pass. Внутри URL и анкора `^` не имеет специального значения.

### 5.3. Голые URL в ZML недопустимы

В теле ZML **не должно быть голых URL**. Все ссылки оборачиваются:
- В `[url|анкор]` или `[url]` (см. §5.2) — внешние.
- В `[[nnn]]` (см. §5.4) — внутренние на статью yaniktoim-cms.
- В трек-формат `[url|title|author]` — только внутри `[mus]` (см. §4.8).

Рендер при ZML→HTML **не делает autolink** — это явно не нужно, так как парсер `3_transform.py` при переносе с proza.ru гарантирует что в теле ZML голых URL нет:
- `<a href="http://proza.ru/YYYY/MM/DD/NNN">текст</a>` своего автора → `[[<наш-NNN>]]` (резолв через manifest).
- `<a href="http://other.com">текст</a>` (внешняя) → `[<url>|<текст>]`.
- Голый URL в исходнике (если попался без `<a>`) — `[<url>]`.
- Ссылки на корпус Зоар (`https://imyavel.github.io/zohar-sulam/<chapter>/<NNN>.html`) — `3_transform.py` распознаёт URL, выделяет `(chapter, N)` и переписывает в специальный синтаксис `{chapter|N}` (см. §5.5). Голый Zohar-URL в теле ZML недопустим — только через `{...}`.

### 5.4. Внутренняя ссылка на статью yaniktoim-cms: `[[<art>]]`

Wiki-style. `<art>` — арт-id целевой статьи в формате `XYZ` или `XYZ<n>` (см. §2.3), он же `frontmatter.art`, `manifest.art`, имя файла `<art>.zml` / `<art>.html`:

```
См. предысторию: [[182]]. Продолжение в [[1B5]].
Развитие темы в [[247A]].
```

Рендер при ZML→HTML:
- Читает `manifest.json`, находит запись с `art == <art>`.
- Ставит `<a class="internal" href="<section>/<art>.html">` с **автоматически подставленным заголовком** статьи из `manifest.title`.
- Если арт-id не найден — `<a class="broken">[[<art>]]</a>` + warning в build log: `WARN <art>.zml line <N>: Broken internal link [[<art>]] — no such article in manifest`.

Внутри `[[...]]` допустимы 3-4 символа: одна буква/цифра года + одна для месяца + одна для дня + опциональная одна для multi-per-day suffix. Любой другой контент — парсер не активирует правило, оставляет как обычный текст.

### 5.5. Ссылка на статью Зоара: `{chapter|N}`

Wiki-style для корпуса `https://imyavel.github.io/zohar-sulam/`. Структура там единообразная: `<chapter>/<NNN>.html` (NNN padded к 3 цифрам).

```
В развитии этой темы — {akdama|4}, плюс параллельное место в {beresheet|17}.
```

Парсер видит `{<chapter>|<N>}`:
- `chapter` — slug главы Zohar-sulam: `akdama`, `beresheet`, `noah`, `lekh-lekha`, и т.д.
- `N` — номер статьи в главе (целое, без ведущих нулей; padded автоматически до 3 при формировании URL).

Рендер при ZML→HTML:
- Резолвит через локальный `zohar_index.json` (предкомпилирован из `C:\Users\admin\Heb\Translated\Site\`):
  - `chapter` → `chapter_title_human` («Введение (Акдама)», «Берешит», «Ноах», ...).
  - `(chapter, N)` → `article_title` («"МИ бара ЭЛЕ" Элияhу», и т.д.).
- Ставит `<a class="zohar" href="https://imyavel.github.io/zohar-sulam/<chapter>/<NNN>.html">Книга Зоар. <chapter_title_human>. <article_title></a>`.

Пример выходного HTML для `{akdama|4}`:
```html
<a class="zohar" href="https://imyavel.github.io/zohar-sulam/akdama/004.html">Книга Зоар. Введение (Акдама). «МИ бара ЭЛЕ» Элияhу</a>
```

CSS-класс `zohar` уже определён в `style.css` (золотистый цвет `#7a5a1a` + dotted underline, на hover — solid).

Ошибки:
- Глава не найдена в `zohar_index.json` — `<a class="broken">{<chapter>|<N>}</a>` + `WARN <NNN>.zml line <N>: Broken zohar link {chapter|N} — no such chapter`.
- Статья N не найдена в главе — то же, с уточнением `... no such article in chapter`.

Внутри `{...}` парсер ищет ровно паттерн `\{[a-z-]+\|\d+\}` — любой другой контент остаётся как обычный текст.

### 5.6. Italic: `_слово_` / `_фраза_`

Курсивная эмфаза — уточнение, акцент, обозначение понятия. Парные `_` обрамляют выделяемый текст.

```
Это _каббалистическое_ "ноу хау".
И эта ступень есть _намерение_, превосходящее природу.
```

Рендер:
```html
Это <em>каббалистическое</em> "ноу хау".
И эта ступень есть <em>намерение</em>, превосходящее природу.
```

Правила:
- Открывающее `_` должно стоять на word-boundary слева: пробел, начало строки, открывающая кавычка/скобка/тире.
- Закрывающее `_` — на word-boundary справа: пробел, конец строки, точка/запятая/двоеточие/восклицательный/вопросительный знак, закрывающая кавычка/скобка/тире.
- Внутри `_..._` — любой текст без `\n` и без вложенных `_`. Допустима inline-разметка ZML (`[^N]`, `[[nnn]]`, `{chapter|N}`, `[url|анкор]`).
- Голый `_` в составе слова (`apple_seed`, `Сумма_к_получению`) **не** активирует italic — boundary не сработает.
- В корпусе proza.ru автор использовал `[фраза]` для этой семантики; `3_transform.py` авто-конвертирует `[фраза]` → `_фраза_` по тому же правилу boundary (на python-этапе, до подачи LLM). Случаи, не подходящие под правило, остаются как есть, и оператор обрабатывает их вручную при post-edit статьи в CMS.

### 5.7. CAPS → small-caps

```
А ТЕПЕРЬ ВНИМАНИЕ к этой строке.
```

Целиком-CAPS параграфы и строки стиха автоматически downcase + wrap в `<span class="sb">` (semi-bold). Имена собственные (Орёл, Творец, Адам, Господь, Бог, Ева, Шхина — все падежи и числа) восстанавливаются с заглавной.

Никаких `[caps]`-тегов — оператор просто пишет CAPS, рендер делает остальное.

### 5.8. Маркер заглавного слова внутри CAPS: `^СЛОВО`

Внутри CAPS-куска (параграфа, строки стиха, эпиграфа, цитаты, тела сноски — где запускается CAPS-pass) можно явно пометить отдельное слово префиксом `^` слитно. После downcase это слово сохраняется с **заглавной первой буквы**, остальные буквы — строчные. Сам символ `^` удаляется.

Источник (ZML):
```
ТРОПА ВОИНА ВЕДЁТ ЧЕРЕЗ ^КЛИ К ^НАГВАЛЮ И К ОРЛУ.
```

Результат рендера:
```html
<span class="sb">Тропа воина ведёт через Кли к Нагвалю и к Орлу.</span>
```

Правила:
- `^` работает **только внутри CAPS-куска** (вне CAPS-pass символ остаётся как есть — в обычной строке просто пиши слово с большой буквы).
- Действует **на одно слово** (последовательность буквенных символов сразу после `^`, без пробела). Чтобы выделить два слова подряд — `^СЛОВО ^ДРУГОЕ`.
- Встроенный список имён (`Орёл`, `Творец`, `Адам`, `Господь`, `Бог`, `Ева`, `Шхина` + падежи) **продолжает работать автоматически без маркера**; `^` его дополняет, не заменяет — нужен для слов которых в списке нет (`Кли`, `Нагваль`, `Шхина`, `Кетер`, `Гадлут` и т. п.) либо для авторских выделений.
- Маркер не нарушает CAPS-детекцию: строка `ТЕКСТ С ^КЛИ ВНУТРИ` остаётся «целиком-CAPS» (`^` — не буква).

## 6. Сноски (тело)

В самом конце документа, после всех блоков и секций. Поддерживаются три формы.

### 6.1. Нумерованная сноска: `[^N]:`

```
[^1]: Кли (- ивр. каб.: инструмент, желание, сосуд). См. также: [[078]]

[^2]: Было и есть, здесь есть форма особая.
    Форма подобия свойств — АВАЯ.

[^3]: Я Намерением правлю
    В точности такой судьбою

    [[195]]
```

- Одна сноска — одна `[^N]:`-строка + (опционально) последующие строки с отступом 4 пробела (continuation).
- Между сносками — пустая строка.
- Внутри тела работают: `[^M]`-маркеры на другие сноски, `[[nnn]]`, `{chapter|N}`, `[url|анкор]`, CAPS-pass, `^WORD`.
- Многострочные continuation становятся `<br>` при рендере (для стихотворных сносок).
- id может быть несплошным (1, 2, 4) — рендер уважает `value=` в `<li>`, нумерация в списке сохраняется.
- В тексте основной статьи должен быть `[^N]`-маркер (см. §5.1), который якорит сноску. Если маркера нет — рендер выдаёт warning (см. ниже про анонимные сноски).

### 6.2. Анонимная сноска: `[^]:`

Для случая, когда в исходнике proza.ru внизу статьи стоит «См. также: ...» без связанного маркера в основном тексте. По смыслу это та же сноска, только без привязки. В ZML — отдельная форма:

```
[^]: [[195]]
[^]: [http://proza.ru/avtor/viktor1717|страница автора viktor1717]
[^]: {akdama|4}
```

Поведение:
- Рендер автоматически ставит **префикс «См. также:»** перед телом каждой анонимной сноски.
- В `<ol class="notes">` анонимные идут **после нумерованных**, как `<li class="anon">` без `id`, без `value=`, без `<a class="backref">`-стрелки.
- Внутри тела — обычная inline-разметка (`[[nnn]]`, `[url|анкор]`, `{chapter|N}` и т.д.).

### 6.3. Анонимная сноска с кастомным префиксом: `[^|<префикс>]:`

Если нужно не «См. также:», а другой префикс:

```
[^|Дополнение]: [[078]] — раскрытие темы.
[^|Параллель]: {beresheet|17}
```

Рендер ставит указанный префикс вместо «См. также:». Префикс может быть любой строкой (включая пустую: `[^|]:` — анонимная сноска вообще без префикса).

## 7. Парсер: грубая семантика

```
1. Расщепить документ на:
   - frontmatter (---...---)
   - body
   - footnotes (хвост, всё начиная с первого `[^...]:` — нумерованного, анонимного `[^]:` или кастомного `[^|...]:`)
2. Body → split по строкам "## <text> {slug?}" → intro + sections[].
3. Каждая секция (включая intro) → split по пустым строкам → blocks[].
4. Для каждого block:
   - "[num]...[/num]" — нумерованная группа параграфов; внутри обычные параграфы через пустую строку, каждый становится `<li>`
   - "[poem]...[/poem]" — поэма
   - "[epi]...[/epi]" или "[epi cite=\"...\"]...[/epi]" — эпиграф
   - "[epil]...[/epil]" — эпилог (спящий)
   - "[quote]...[/quote]" или "[quote cite=\"...\"]" — цитата (спящая)
   - "[sub]...[/sub]" — подзаголовок (h2-эхо)
   - "[mus]...[/mus]" или "[mus=\"<label>\"]...[/mus]" — music-группа; внутри построчно "[url|title|author]"
   - иначе — параграф (одиночный или последовательность через пустую строку)
5. Внутри каждого block (inline-разметка), порядок:
   - [^N] (footnote marker) → временный токен
   - [[nnn]] (internal link) → временный токен
   - {chapter|N} (Zohar link) → временный токен
   - [url|анкор] / [url] (external link) → временный токен
   - _italic_ → временный токен (см. §5.6)
   - CAPS-pass + ^WORD (см. §5.7 и §5.8)
   - временные токены раскрываются обратно в финальный HTML
6. Footnotes → list[{id|null, prefix|null, body_html}]:
   - `[^N]:` → `id=N, prefix=null` (нормальная нумерованная).
   - `[^]:` → `id=null, prefix="См. также:"` (анонимная).
   - `[^|text]:` → `id=null, prefix=text` (анонимная с кастомным префиксом).
   Все проходят inline-разметку как обычный текст. В рендере нумерованные идут первыми с `<a class="backref">`, анонимные — после с `<li class="anon">` без backref.
7. Warning при `[a|b|c]` (3 параметра) вне `[mus]` — см. §4.8.3.
```

## 8. Открытые вопросы

- ~~(Q) ASCII скобки `[tag]` vs Unicode `⟦tag⟧`~~ — **решено: ASCII** (2026-05-28). Существующие Unicode-маркеры в `transform_prompt.md` будут переделаны при ревизии архитектуры pipeline (см. roadmap → TODO).
- ~~(Q) Имя расширения файла~~ — **решено: `.zml`** (2026-05-28). Расшифровка не «yaniktoim markup language» (там был бы конфликт с YAML — `.yml`), а просто `.zml` как мнемоника проекта.
- ~~(Q) `[^N]` (Markdown-style) vs `[fn:N]`~~ — **решено: `[^N]`** (2026-05-28). Короче и привычно тем кто знаком с Markdown footnotes.
- ~~(Q) Формат гиперссылки~~ — **решено: `[url|анкор]`** pipe-style (2026-05-28, переопределено над прежним Markdown-стилем). Унифицирует с трек-форматом `[url|title|author]` внутри `[mus]`. Внутренние ссылки на yaniktoim-cms — отдельный синтаксис `[[nnn]]` (§5.4). Голых URL в теле ZML быть не должно — все ссылки в тегах (§5.3). Парсер на этапе ZML→HTML обрабатывает в порядке: `[^N]` → `[[nnn]]` → `{chapter|N}` → `[url|анкор]` → CAPS-pass → `^WORD`.
- ~~(Q) Music-формат~~ — **решено: `[mus]...[/mus]` с трек-строками `[url|title|author]`** (2026-05-28). Заменяет прежний self-closing `[music perf="..." title="..." url="..."]` с правилом наследования label. Группа теперь явная (один контейнер на группу), label единый через `[mus="..."]` или дефолт. См. §4.8.
- ~~(Q) Оставлять ли в спеке `[epil]`/`[quote]`~~ — **решено: оставить** до первого появления (2026-05-28). Теги «спят» в SPEC §4.5 и §4.6, но не используются в transform-парсере и в demo. Когда впервые встретятся в исходниках на этапе ревизии — активируем.
- ~~(Q) Нужен ли тег для параграфов?~~ — **решено: одиночные параграфы остаются default без тега; новый тег `[num]` (§4.2) только для нумерованных групп** (2026-05-28). Симметрии со стихом не добиваемся — параграф самый частый блок, тег давал бы шум.
- ~~(Q) Italic как inline-тег?~~ — **решено: `_слово_` / `_фраза_`** (2026-05-28). Авторские `[фраза]`-пояснения в корпусе proza.ru авто-конвертятся в `_фраза_` на этапе `3_transform.py` по правилу word-boundary (см. §5.6). Все 17 случаев парных `_..._` в чистом тексте — это голые URL, которые уходят в `[url]`-обёртку, поэтому в теле ZML не пересекаются.
- ~~(Q) Формат id статьи?~~ — **решено: арт-id `XYZ[n]`, кодирует date_chosen** (2026-05-28). Замена прежней последовательной нумерации `001..350`. См. §2.3. Преимущества: легко добавлять «найденные старые» статьи без сдвига последующих; короче (3-4 символа); сортировка по дате тривиальна.

См. `demo.zml` (минимальный пример) и `demo.html` (отрендеренный вид).
